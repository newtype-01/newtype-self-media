# 从 Workflow 到 Skill

把已经稳定的做法写成可触发、可执行、可检查的 Skill。Skill 来自实践，不来自对理想流程的想象。

## 准入检查

开始前确认：

1. 同一流程已经运行至少三次。
2. 三次的主要步骤大体相同。
3. 输入和输出文件已经稳定。
4. 已经知道哪些地方必须人工判断。

如果条件不足，只能输出“Workflow 草案”和待验证项，不能声称 Skill 已验证。

## 读取材料

- 三次或更多任务记录。
- 对应输入、阶段产出和最终产出。
- 修改记录、复盘和失败案例。
- 当前项目结构及真实文件名。

只提炼多个运行共同支持的规则。一次偶发问题不应自动升级成永久规定。

## 工作流程

1. 比较各次运行，列出稳定步骤、可选步骤、失败点和人工确认点。
2. 定义一个窄任务范围，并列出明确不适用场景。
3. 选择简短、可区分的英文名称，使用小写字母、数字和连字符。
4. 写清触发描述、必要输入、执行阶段、输出、质量检查和停止条件。
5. 把只有特定模式才需要的长说明放入 `references/`，不要让入口文件变成教程。
6. 检查路径、工具和产品能力是否真实存在。
7. 保存为草案，先运行真实任务，再根据观察修改。

## 输出

默认输出：

```text
skills草案/<skill-name>/SKILL.md
```

如果用户已经明确要求安装，并且目标环境的 Skill 目录已确认，可以复制到对应目录。不得自行修改全局 Skill 或覆盖现有版本。

## 人工确认

- Skill 的任务边界、名称和触发描述。
- 哪些项目约定应成为可复用规则。
- 是否安装、替换或公开发布 Skill。
- 修改会影响以后所有同类任务时，先展示差异再覆盖。

## 验证

- frontmatter 包含正确的 `name` 和可区分的 `description`。
- 另一个没有参与设计的人或 Agent 能根据真实材料完成任务。
- 缺少必要输入时会停止，不会编造。
- 不自动发布，不把外部操作授权写进 Skill。
- 不创建一个覆盖选题、写作、视频、复盘和自动化的万能 Skill。
